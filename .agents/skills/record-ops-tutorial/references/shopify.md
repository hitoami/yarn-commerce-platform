# Shopify 业务边界与恢复

制作 Shopify 教程时读取；当前 `PRODUCT.md`、`CONTEXT.md` 和本次授权优先。以下是核对方法，不是历史店铺状态快照。

## 先确认维护对象

| 内容 | 本流程中的定位 | 教学重点 |
|---|---|---|
| 毛线 / 手工成品 | Shopify Product 及 Variant | 内容与交易字段分开；颜色、克重、SKU 不能混淆 |
| 材料包 | 编织作品等内容条目与其关联毛线 | 展示简介、关联商品规格、建议采购数量；不为演示新建独立材料包商品或库存 |
| 本季主推 | 对应页面与模板的内容设置 | 从页面进入正确模板，选择对应语言；内容保存不等于发布新 Theme |
| 库存 | Variant 与库存地点 | 区分可用、预留、现货；网站核对同一规格 |

这些入口可能随实现变化，必须现场确认。查询与批量写入遵守 AGENTS.md 的 `npm run admin` 规则；用户已明确授权录制单条 UI 修改时展示真实操作，不扩展为批量写入，也不为了录屏另找凭证。

## 内容修改恢复

- 修改前保存精确原文和资源身份，只保存在任务本地。使用可辨认的临时标记，范围尽量小。
- 保存成功后刷新对应语言的网站页面，证明内容确实出现；恢复原文后再次保存、刷新并核对。
- 如果期间有人修改同一字段，不能直接覆盖为旧备份。先确定哪些是本次演示改动，保留他人的修改；无法区分时停止写入并说明冲突。
- 只查看图片或字段入口时，讲解写「查看入口」，不能声称已完成图片替换或整页内容维护。

## 库存恢复

- 基线至少包括规格、SKU、库存地点、可用/预留/现货数量及最近调整历史。所有演示值与恢复操作都应在授权范围内。
- 「设为」是最终数量；「调整」是增减量。保存前读回数值，检查错误追加导致的 `10` 等情况。
- 数量变化后，在网站选中同一色号和重量，核对售罄或加入购物车状态。不能拿其他仍有货的规格证明恢复。
- 恢复前再看历史和订单，确认是否有并发销售、预留或其他人调整。只逆转本次演示的变化；不能一律把库存设回起始数。
- 重新打开后台核对当前数量，再刷新网站。调整历史某列出现「无变化」时，不能仅凭该列推断失败或成功，要结合现货变化、当前数量与网站结果。

## 下单与交货演示

- 先核对当前支付模式、市场/结账地区、运费和受控测试收件人。测试模式未确认时，不为了拍片提交可能真实扣款的订单；请求必要决定或改成只读演示。
- 演示订单、履约单号、地址和通知都必须在本次授权范围内。明确标识测试；不要填看似真实、可能指向其他包裹的物流号码。
- 单号可用显式演示格式，承运商与 URL 不确定时不要编造。后台「已发货」只证明标记履约，不证明揽收、运输或签收。
- Shopify 显示邮件「已送达」是平台记录；只有实际查看受控邮箱才可说「邮箱已收件」。自动邮件中的运输文案不是承运商证据。
- 画面涉及外国测试地址或临时运费时，明确它不能证明日本正式结账和配送；模拟退款也不能证明真实资金退款或银行结算。
- 日本现货、中国代发、混合订单可用标注「待确认」的卡片解释。没有实拍和证据时，不把贴标、包装、分包、揽收或签收列为通过。

结束时按实际订单状态处理：必要时先撤销测试履约，再取消测试订单并核对测试退款与补回库存；核对是否已自动补回，避免手动重复增加。使用当前 UI 与平台状态，不假设每种订单都能走同一按钮路径。若有真实支付、真实发货或状态不明，先核实权限与后果，不能机械执行清理。

复核订单状态、净支付/退款记录、履约状态、库存及测试购物车。保留订单审计记录，不以永久删除代替恢复。UI 仍显示旧状态时刷新重新读取，不能根据过期标题重复取消或退款。

视频结束的结论应分清：系统操作与状态变化已验证什么；实际收到或交付了什么；真实营业尚需哪些验收，例如日本结账、正式运费、收款到账、真实退款、承运商揽收与签收。

不要为录制默认额外建立真实订单。需要真实业务验收时，把具体方案留给当前 Issue，并按生产安全规则取得当次授权。
