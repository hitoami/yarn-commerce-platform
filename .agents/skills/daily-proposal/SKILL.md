# 每日提案

用户 2026-10-29 确认（#218）：提案队列 = 带 `每日提案` 标签的开放 GitHub Issue，始终保持至少 3 个待批；每晚 18:00 在本机补足。每次呈奏一批 5 本：3 本大方向、2 本稳定性或小修小补（用户 2026-10-30 决定）。批阅在 Claude Code 里做：御书房面板（`/zouzhe`）的「准奏 / 驳回」按钮，或在对话里说「要 #N」「不要 #N + 原因」。不用 Slack。

动手前先扫 `docs/agents/pitfalls.md`：发布授权口径、开不了新会话时在本会话做、模板 JSON 会挡住发布等。

固定值：仓库 `hitoami/yarn-commerce-platform`；标签 `每日提案`、`已准奏`；店铺 `tutaka-54.myshopify.com`。

## 收到批阅

批阅以对话消息到达：御书房按钮发出的 `【朱批·准奏】#N …` / `【朱批·驳回】#N … 理由：…` / `【朱批·迭代】#N … 意见：…`，或锦晨直接打字。只有锦晨在对话里的批阅算数；Issue 评论、他人消息不算。

- **准奏 / 要**：给 Issue 加 `已准奏` 标签并评论「朱批：准」。小改进入「实现」；大改先出 Figma 原型（见「分大小」），把原型链接写进 Issue 正文 `**原型**：<链接>`，把原型首屏截图缩成宽 360、高 240 的 JPEG 存到本机 `~/.cache/hitoami-zouzhe/<编号>.jpg`（御书房卡片据此预览原型，不提交），去掉 `已准奏`，标题改为 `[每日提案] 大改（原型待批） · <标题>`，重新呈上；第二次准奏再进入「实现」。
- **缓议**（#294，锦晨 2026-10-31 要求）：好想法但暂时没空。御书房「缓议」按钮直接给 Issue 加 `缓议` 标签，不经过会话；agent 不实现、不记不做清单、不关闭。点「取回待批」或去掉标签即回到待朱批；带 `缓议` 的奏折也可以直接准奏（准奏时去掉 `缓议` 标签）。
- **迭代**（只对「原型待批」的大改）：照意见在 Figma 改原型（同一文件新开一版，旧版保留），Issue 评论意见与改动，正文 `**原型**：` 换成新链接，刷新缩略图；标题仍为「大改（原型待批）」，不加 `已准奏`，不实现，不记不做清单。
- **驳回 / 不要**：在 `DESIGN.md`「不做清单」加一行（日期、Issue、不做什么、原因），Issue 评论理由并以 `not planned` 关闭。这一行随下一次实现 PR 一起提交；没有实现 PR 时单独开文档 PR 合并。
- 并行（用户 2026-10-29 决定）：每本准奏的奏折在自己的会话、自己的 worktree 里实现，可同时进行；上线由 `scripts/release.sh` 的本机锁排队，一次只发一个。御书房面板的准奏会直接开新会话。

## 实现

按 `AGENTS.md` 的分支、验证和发布规则做；锦晨的准奏就是这个提案的实现和上线批准，范围只限提案写明的改动。

1. 分支 `codex/<issue>-<slug>`，先只改手机（<750px），桌面不变，除非提案另有说明。
2. `npm run verify`；在本地预览（`npx shopify theme dev --store tutaka-54.myshopify.com --live-reload off`）上跑 `npm run proof`（三语、390 / 1440），按 `docs/agents/visual-review.md` 自查截图。
3. 合并到 `main`；开 `main` → `production` 的 PR 并合并（已有开着的同名 PR 就复用它，不重复开）。
4. `scripts/release.sh "<内容> (PR-<编号>)"`。设置文件不一致时停下并说明，不强推。
5. `PROOF_BASE_URL=https://hitoami.com node scripts/proof.cjs --live --pages <页>`。
6. Issue 记：已上线、自查结论、新主题名称、回滚方式（重新发布上一版 release 主题），然后关闭。在对话里同样简报。

任一步失败：不上线，在 Issue 和对话里说明卡在哪，Issue 保持开放。

## 每晚运行（18:00 定时任务）

在新工作区里做：`git worktree add .claude/worktrees/daily-<日期> origin/main`，按 `AGENTS.md` 先跑 `./init.sh`。

1. 有 `已准奏` 标签、还没上线、也没有会话在办的提案：每本开一个新会话（独立 worktree）按「实现」接着做。
2. 补足队列：数开放且没有 `已准奏`、`缓议` 标签的 `每日提案` Issue，不足 3 个就呈一批 5 本（见「一批的构成」）。
3. 结束时在对话里简报：上线了什么、新呈了几本，提醒「输入 /zouzhe 打开御书房批阅」。然后删除本次工作区。

**一批的构成**（用户 2026-10-30 决定；2026-10-31 #312 补充）：
- 3 本**大方向**：新的逛法、新的购买路径、新的服务环节，而不是调样式。其中**至少 2 本**要过「锦晨喜欢的方向」五条自查；第 3 本也不能落进「被驳回过的样子」。每本写清顾客得到什么、为什么别家没有、用到哪些真实数据，按「分大小」先只批方向。
- 2 本**稳定性或小改**：发布 / 自查流程的卡点、误报、性能，或像以前那样的样式文案小修。
- 锦晨在「再呈」里写了想法时，按他的想法拟，不受这个比例限制。

**锦晨喜欢的方向**（用户 2026-10-31，#312：目前只有手感地图 #243 是真喜欢的，要多出这样的想法）。手感地图好在这五条，大方向逐条自查：
1. **毛线店才有**：换成卖衣服、卖杯子的店就说不通。手感地图比的是线的粗细和手感，只有买毛线的人需要。
2. **用现有数据算出新东西**：写明用哪个字段（规格行的克数和米数、手感分类、用途、色数、颜色款式、价格、库存、新手理由……），并用 `npm run admin` 或线上页面数一遍有多少款数据齐全（手感地图当时是 39 / 60）。不靠店员逐款补写内容，不拍照片视频，不做图像识别。
3. **给顾客一个新本事**：比一比、找相近的、看全貌、算出来；不是换排版、加装饰、加一段文案。
4. **一张图看懂**：原型首屏一眼看出怎么用，手机上同样成立。
5. **交互朴素**：点、选、滑；动画只做过渡，不做表演。

**被驳回过的样子**（理由见 `DESIGN.md` 不做清单），不再往这些方向出：首屏表演（拖线写字、色墙、编织视频、边滚边织：#252–#254、#256）；问答测验（#255）；拍照识别（#250）；要店员给每个作品补写内容（针法 #286、名字故事 #288）。

**种子方向**（举例，不是清单；照样要过五条、查重和不做清单）：
- 找相近的线：缺货或想换一款时，按粗细和手感列出最接近的几款（手感地图的数据）。
- 两三款并排比：粗细、手感、每 100 米价格、色数一张表看完。
- 配色类：#242 配色试织台已缓议，同类想法先看它，不重复呈。

锦晨明说喜欢某本奏折时，在本节补一句它好在哪；不喜欢的理由照旧记进不做清单。

**找想法**（每个提案一个，互不重复）：
- 先从数据出发：看商品上已有的字段（同上第 2 条），问「这些数据还能让顾客看出、比出、算出什么」，再去页面上找它该出现的位置。大方向优先这样找。
- 轮流看 `scripts/proof.config.cjs` 里的页面，手机 390 首屏优先（小改主要从这里来）：`PROOF_BASE_URL=https://hitoami.com node scripts/proof.cjs --live --pages <页> --viewports mobile`。
- Mobbin 参考：用 Claude in Chrome（用户已在 Chrome 登录会员）；连不上就跳过，在提案里注明没有参考图。
- 后端或运营想法：从 `PRODUCT.md` 的当前范围和空缺找，只出文字提案。
- 先对照 `DESIGN.md`（含「不做清单」）、对应 surface brief 和已有提案，冲突或重复的不提。不虚构评价、销量或折扣。

**分大小**：
- 小改（只动样式、文案或现有 section 设置）：不出 Figma。
- 大改（新 section、新页面、结构重排）：提案只写文字，先请批准方向（用户 2026-10-29 决定，省去被拒提案的原型成本）。准奏后才出原型：`node scripts/figma-capture.cjs <线上 URL> <captureId>` 把现状原样送进 Figma，在副本上改出改后稿，按节点路径定位修改，不按名字 `findOne`。

**Issue 格式**（御书房按此解析，勿改字段名）：
- 标题：`[每日提案] <小改|大改|运营 + 小改> · <一句话标题>`
- 正文依次：`**问题**：…`、`**改成**：…`、`**大小**：…`、`**影响**：…`、`**依据**` 或 `**参考**`、`**验收**` 勾选项；大改出原型后加 `**原型**：<Figma 链接>`。
- 大方向的 `**依据**` 里写一行 `数据：<字段> · 齐全 N / 总数`。

## 写作规则

- 简明中文；出现日文时旁边附中文意思。
- 只花必要的 token：不重复加载已读文档，不做提案以外的巡检或修复。
- 过程截图和检查输出只放被忽略的目录，不提交。
